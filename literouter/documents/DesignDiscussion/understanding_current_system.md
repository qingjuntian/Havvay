这是一个非常关键的尽调问题。在把现有系统升级或集成到我们的网关之前，必须先摸清它的**真实能力边界和债务**。以下是你应该集中提问的六个角度，每个角度都对应我们设计中的关键假设，能直接暴露迁移风险：

## 1. 计费与资金模型（最高优先级）

这是最容易出生产事故的地方：

- **计费单元**：现在按什么计费？（每次调用/token 数/固定套餐/后付费？）
- **资金可靠性**：是否已有预留、幂等结算、防重复扣费机制？还是简单的"调用后扣余额"？
- **成本归因**：能否区分"客户调用的成本"和"平台自己的成本"？还是混在一起？
- **对账能力**：出现网络超时、服务崩溃后，能否确定"到底执行了没有、该不该收费"？

**为什么重要**：我们的设计（Doc 02/03）假设了预留-结算-账本的严谨模型。如果现有系统是"先扣钱再说"或"无法区分成功/失败计费"，迁移到我们的模型时，历史数据和客户预期会有巨大冲突。

## 2. 多 Provider 接入深度

- **Provider 覆盖**：现在接了几家？每家是深度集成（协议转换、错误归一化）还是简单转发？
- **能力注册表**：是否已有模型能力数据（上下文长度、工具调用、结构化输出支持），还是硬编码在代码里？
- **协议差异**：流式输出、工具调用、JSON 模式等是否真正统一，还是各 Provider 各写一套？

**为什么重要**：我们的智能路由依赖 Doc 04 §8 的能力注册表。如果现有系统只是"能调通"但没有结构化的能力数据，迁移时需要补大量元数据，否则阶段感知路由无从谈起。

## 3. 请求生命周期与可靠性

- **重试策略**：现在如何处理超时？是立即重试、标记失败，还是保留状态？
- **幂等性**：客户端重试（网络问题或用户刷新）会产生重复请求吗？
- **流式处理**：长连接断开时，如何确定 Provider 实际生成了多少内容？

**为什么重要**：Doc 03 §8.3 明确规定"超时本身不是重试依据"。如果现有系统习惯于"超时即重试"，迁移后客户可能会觉得"变慢了"或"不智能了"，需要预期管理。

## 4. 多租户与安全边界

- **隔离粒度**：租户是组织、团队还是个人？API Key 的权限模型是什么？
- **数据隔离**：不同租户的数据（请求、日志、计费）是否物理或逻辑隔离？
- **合规能力**：是否支持区域路由（如欧盟数据不出境）、ZDR（零数据保留）？

**为什么重要**：Doc 05（安全设计）还未完成，现有系统的安全模型将直接影响我们的 Doc 05 范围。如果现有系统权限模型混乱，迁移时可能需要重构客户身份体系。

## 5. 可观测性与数据基础

- **日志与追踪**：能否追踪"一次用户请求 → 哪个模型 → 哪个 Provider → 实际成本"的完整链路？
- **效果反馈**：客户或系统能否标记"这次生成的代码通过了测试"？
- **历史数据**：是否有足够的历史调用数据（输入、输出、延迟、成本、结果）用于训练或验证路由策略？

**为什么重要**：我们的数据飞轮（任务级反馈优化路由）依赖这些信号。如果现有系统是"黑盒"，我们需要从零开始积累数据，MVP 验证周期会拉长。

## 6. 现有客户的使用模式

- **调用模式**：客户主要是单轮问答，还是已有长时程 Agent 任务？
- **集成深度**：客户是直接调 REST API，还是通过 SDK？SDK 是否已包含 metadata 传递机制？
- **痛点反馈**：客户目前抱怨最多的是什么？（成本？速度？稳定性？模型能力？）

**为什么重要**：如果现有客户全是单轮问答，那么我们的"任务感知"价值需要重新教育市场；如果已有 Agent 客户，他们可能已有自己的任务编排逻辑，我们需要明确 Gateway 与 Runtime 的边界（ADR-0401）。

---

**建议的提问顺序**：先问 1（钱）和 4（安全），这两个决定能否合规运营；再问 2 和 3（技术债），决定迁移工作量；最后问 5 和 6（数据和市场），决定 GTM 策略。
